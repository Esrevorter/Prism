## 1. Project snapshot (one paragraph)

Prism (PRI) is a privacy-focused reference coin with a zero-dependency Python
core, a local GUI wallet, and a lean authentication model. Since
**spec Amendment A2-2026-10**, the multi-device MPC/FROST ceremony is retired
and replaced by a password-sealed local spend key (`prism/auth/keystore.py`)
plus a single-use, intent-bound image-grid CAPTCHA gate (`prism/auth/captcha.py`)
before every signature. Testnet parity with production validation is enforced
by dedicated tests. Current release: **v0.1.13** — the first *production*
release (all prior releases deleted per founder request; only v0.1.13 remains
on GitHub Releases with Windows/macOS/Linux installers, CLI binaries,
SHA256SUMS, and cosign signatures). v0.1.11–13 history: visible build stamp +
GUI-bundle fingerprint in the footer (`/health`), `Cache-Control: no-store`
on all GUI responses (root cause of "nothing ever changes" complaints was a
stale WebView2 cache), golden-P brand icons generated by `scripts/make_icon.py`
(release gate now rejects blank icons), rules file at v1.4+ with §7 documenting
the real data dir `~/.wallet` (`C:\Users\<name>\.wallet` on Windows 11 — NOT
%LOCALAPPDATA%).

## 3. Environment & setup (reproduce in any fresh sandbox)

```bash
cd /workspace                      # git repo, branch main
python -m pytest prism/tests -q    # full suite (~110 s), no deps beyond stdlib+pytest
node --check prism/gui/app.js      # GUI controller syntax check
bash packaging/build_release.sh    # Linux binary -> dist/prism (PyInstaller can't cross-compile)
python scripts/publish_wiki.py     # push wiki/ -> hosted GitHub wiki (needs write token)
```

Credentials (policy amended Oct 14): the sanctioned write-auth path for
coder.qwen.ai sessions is a **user-managed fine-grained PAT injected via the
platform UI**, not typed into any agent command. Configure under
**Settings → Environments → Edit "Prism"**:
- *Environment variables:* one entry — `GH_TOKEN=<fine-grained PAT>` (repo-scoped,
  Contents: Read+Write, Pull requests: Read+Write; no more permissions than needed).
- *Setup script:* register the token with git so pushes/PRs work all session:

  ```bash
  git config --global credential.helper store
  printf 'https://x-access-token:%s@github.com\n' "$GH_TOKEN" > ~/.git-credentials
  chmod 600 ~/.git-credentials
  unset GH_TOKEN   # keep it out of the shell environment once registered
  ```

Rules that still apply: agents must NEVER hardcode, echo, commit, or log the
token value; no tokens embedded in remote URLs or `.git/config`; the token lives
only in the platform UI settings and `$HOME/.git-credentials` (sandbox-local,
never committed). Keep secrets out of the repo itself — do not add a `.env` file
with credentials to version control. If neither the PAT nor an OAuth connection
is available in a session, run unauthenticated reads (`git ls-remote` works on
this public repo) and report write-side status as UNVERIFIED — never fabricate
the push (rules.md §4).

**Session-start env-var error — platform bug, not a repo bug (added Oct 13,
corrected same day):** sessions on coder.qwen.ai may open with
`Oops! There was an issue connecting to Qwen3-Coder. Failed to set env var:
ERROR: No previous running command to retrieve logs from.` This is emitted by
the platform's own per-session "set env var" hook when it tries to apply a
variable configured in the coder.qwen.ai UI settings into the freshly created
sandbox shell (its log-retrieval call runs before any prior process exists).
It is NOT caused by anything in this repository: exhaustive grep confirms no
`.md` file (root, `docs/`, `docs/internal/`, `wiki/`) contains any instruction,
script, or snippet that sets environment variables, so no doc change can fix
or prevent it. It is also transient — the first tool call after the error
succeeds. Agents should ignore the message, proceed with unauthenticated reads,
and rely on the OAuth connection for writes. Report it upstream to Qwen Code
instead of working around it in-repo.

## 4. Conventions (hard rules distilled from spec + sessions)

1. **Honest UX everywhere:** no invented reassurance text; server-computed
   `human` fields drive UI copy; CAPTCHA framed as presence-check, never as
   identity proof.
2. **Single source of truth:** GUI edits go to `prism/gui/`, then run
   `packaging/sync_gui.py`; wiki edits go to `wiki/`, then publish.
3. **Version bumps touch all five places:** `pyproject.toml`,
   `prism/chain/__init__.py::__version__`, `packaging/tauri/prism-gui/src-tauri/tauri.conf.json`,
   `.../src-tauri/Cargo.toml`, `.../package.json`. (Formerly listed a nonexistent
   `desktop/src-tauri/` prefix — corrected Oct 13; `release_gate.py` checks these paths.)
4. **Tags trigger releases:** annotated tag `vX.Y.Z` → release.yml +
   desktop.yml build and publish artifacts automatically. Prerelease flag
   until mainnet candidate.
5. **Tests gate everything:** never merge/tag with a red suite; new features
   land with pinned tests (see `test_lean_auth.py`, `test_testnet_parity.py`).
   Tests must exercise the WIRE payload only — never reach into server
   internals like `captcha._pending` to cheat a check that real clients
   would fail (this exact cheat hid the v0.1.7 broken captcha from CI).
6. **Release gate is mandatory:** run `python scripts/release_gate.py <X.Y.Z>`
   before tagging, and re-check the published GitHub Release page title/body
   version string after the workflow finishes (v0.1.7 shipped labeled 0.1.0).
   The gate also runs in ci.yml and as the first step of release.yml.
7. **Legacy code stays unless proven dead:** retired modules keep their
   property/fuzz coverage; wire-level references get deleted.

## 7. Known pitfalls (each cost a debugging session once)

- **Tauri `dist/index.html` is a boot screen**, not the GUI bundle. Copying
  `prism/gui/index.html` over it breaks sidecar startup. (True story.)
- **Token capability claims decay and must be re-probed every session.** History here:
  Oct 12 claimed fine-grained PATs get 403 on issue-milestone writes ("platform
  limitation"); Oct 13 could not reproduce ANY successful authenticated API call (the
  pasted fine-grained PAT now returns 401 on a plain GET — treat all chat-pasted tokens
  as burned). Net lesson: never write "X cannot do Y" without the exact request+response
  pasted alongside, and never trust such a claim from a previous session (rules.md §4).
  Confirmed-still-true separately: fine-grained PATs cannot push the hosted wiki (needs
  classic `repo` scope or workflow GITHUB_TOKEN). Pushes that "succeed"
  locally may still not land remotely: **always verify with `ls-remote`/API**.
- **PyInstaller on macOS runners** needs the framework layout shim
  (`.github/scripts/macos_framework_shim.sh`); standalone CPython alone fails.
- **GitHub's `permissions` field on fine-grained tokens reflects the user, not
  the token** — probe writes to know the truth.
- **setup-python `cpython-3.12` is unresolvable** on arm64 macos-26 runners;
  use default + shim instead.
- **The hosted wiki needs a manually created first page** once per repo before
  any git push to `*.wiki.git` works.
- Never trust prior-session claims of completion — re-verify against the repo
  and GitHub API at session start (this exact failure mode produced false
  "published" reports twice; fixed by making verification part of the protocol).
- **Session-start env-var error on coder.qwen.ai (reported + corrected Oct 13):**
  every new session whose UI settings contain a configured environment variable
  opens with `Oops! There was an issue connecting to Qwen3-Coder. Failed to set
  env var: ERROR: No previous running command to retrieve logs from.` Confirmed
  NOT a repo bug and NOT agent shell-tool usage: no `.md` file in this repository
  sets or instructs setting env vars (see §3). The platform hook that injects the
  UI-configured variable into the fresh sandbox shell calls log-retrieval before
  any prior process exists, so it errors — then the connection reset kills the
  first remote read. Workaround for agents: ignore the message, re-run the read
  (`git ls-remote` works unauthenticated on this public repo), and authenticate
  publish/PR steps via the UI-configured `GH_TOKEN` + setup script (§3) or the
  OAuth connection — never type token values into commands yourself. Upstream
  fix belongs to coder.qwen.ai: apply session env vars as a foreground export
  at shell creation, not a log-fetch on a nonexistent process. Removing the
  variable from the UI settings also stops the error until then (at the cost of
  losing write auth).

## 8. Documentation flow

`spec.md` (decisions) → code + tests (evidence) → `wiki/` (human docs, source
of truth) → `scripts/publish_wiki.py` → hosted wiki (rendered copy).
README badges/links point at live release + live wiki. When editing docs, ask:
"would a first-time user find this on the hosted wiki?" — if yes, edit `wiki/`
and republish; if developer-facing, `docs/` or README is fine.

## 9. Resume protocol (for the next agent session — follow exactly)

0. Bootstrap: read `AGENTS.md` (repo root) and follow its sequence — it loads this
   file and the governance chain in the correct precedence order.
1. `git fetch origin && git log --oneline origin/main -5` — reconcile local vs
   remote HEAD; fast-forward if behind. If the session opened with the platform's
   "Failed to set env var … No previous running command to retrieve logs from"
   message (see §3), that is a coder.qwen.ai startup-hook error, not an auth
   failure and not caused by this repo — do NOT type token values into commands
   yourself. Retry the read; use unauthenticated
   `git ls-remote` (works on this public repo) if needed, and perform all
   write-side steps (push/publish/PR) via the UI-configured `GH_TOKEN` + setup
   script (§3) or the configured OAuth connection.
   Mark write-side status UNVERIFIED until an authenticated operation succeeds.
2. Read §5/§6 here: pick the top open thread the user confirms.
3. Run `python -m pytest prism/tests -q` **before** changing anything; a red suite
   means resume debugging, not feature work.
4. Make the change; update this file's §5/§6/Last-updated line in the same
   commit (maintenance rule).
5. Push/verify: after every push, confirm with `git ls-remote` **and** the
   GitHub API (contents/commits endpoint) that the remote actually has it.
   Report only what was verified. Never claim success from exit codes alone.
6. For releases: bump versions (§4.3), annotated tag, watch the three
   workflows to completion, spot-check release assets via API, then tidy old
   runs/releases only when asked.
